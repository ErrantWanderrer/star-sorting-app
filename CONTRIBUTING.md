# CONTRIBUTING.md — правила командной работы

## 1. Общие принципы

- Работаем через **ветки + Pull Request (PR)**. Прямой push в `main` **запрещён**.
- Ветка = 1 человек = 1 модуль.
- Долгие ветки — зло. Ветка живёт **максимум 2–3 дня**, потом PR.
- Перед началом работы и перед PR — **`git pull` актуального `main`**.
- После мерджа **ветку удаляем**.

---

## 2. Ветки

| Ветка | Владелец | Что делает |
|---|---|---|
| `feature/model` | лид | Контракты (интерфейсы) + модель + Builder + валидация + компараторы |
| `feature/sorting` | #2 | `SortContext`, алгоритмы, 3 поля, доп.1 |
| `feature/collection` | #3 | Кастомная коллекция (3\*), доп.4 (многопоточность), интеграционные тесты |
| `feature/filling` | #4 | Заполнение (файл/рандом/руками), доп.2, доп.3 |
| `feature/ui` | #5 | Главный цикл, меню, интеграция всего |

### Как создать ветку

```bash
git checkout main
git pull
git checkout -b feature/название
```

Ветку режем **всегда от актуального `main`**, не от чужой ветки.

---

## 3. Коммиты

Формат: `тип(модуль): что сделано`

Типы: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`.

Примеры:
```
feat(model): add Student class with Builder and validation
feat(sorting): add BubbleSort strategy
feat(sorting): add odd/even sorting (extra task 1)
fix(filling): validate empty file lines
test(collection): add tests for custom list resize
docs: add README with run instructions
```

Правила:
- 1 коммит = 1 логическое изменение (не «куча всего за раз»).
- Осмысленное сообщение, не `fix`, `update`, `asdf`.
- Коммитим **часто** (не один коммит на всю ветку) — по `git log` видно вклад каждого.

## 4. Pull Request

### Перед созданием PR

```bash
git checkout main
git pull
git checkout feature/твоя-ветка
git merge main          # подтянуть свежий main в свою ветку
# прогнать проект локально, убедиться, что собирается и работает
git push
```

### Шаблон PR (копируй в описание)

```markdown
## Что сделано
- ...

## Какие задачи закрывает
- [ ] ...

## Как проверить
1. ...
2. ...

## Чек-лист
- [ ] Собирается и запускается
- [ ] Нет `Collections.sort` / `Arrays.sort` / готовых паттернов
- [ ] Нет Lombok
- [ ] Есть тесты на новый код
- [ ] Код-стайл по Java-конвенциям
```

### Правила ревью

- Ревьюер — **лид** (или назначенный им человек).
- Минимум **1 approve** перед мерджем.
- Замечания обсуждаем в PR, не в личке.
- Конфликты разрешает **автор ветки** (у себя локально), не ревьюер.

## 5. Кто какие файлы трогает (антиконфликт)

> **Правило №1: не лезь в чужие файлы без согласования.**

| Зона | Кто трогает | Комментарий |
|---|---|---|
| `SortStrategy`, `DataFiller`, `CustomList` (интерфейсы) | **только лид** | Контракты меняются только через лида + обсуждение |
| Модель (`Student`, `StudentBuilder`, компараторы) | только #1 (лид) | — |
| `SortContext` + алгоритмы | только #2 | — |
| Кастомная коллекция | только #3 | — |
| Заполнение (filler’ы, файлы) | только #4 | — |
| `Main.java` / точка входа / меню | **только #5** | Остальные точку входа НЕ трогают |
| Тесты на модуль | автор модуля | — |
| `README.md`, `CONTRIBUTING.md` | лид | — |

**Если нужно поменять чужой файл** — сначала напиши владельцу в чат, договоритесь, кто делает правку.

## 6. Контракты (интерфейсы) — фиксируются в день 1

Лид пушит в `main` первым PR **до старта остальных веток**:

- `SortStrategy<T>` — `void sort(CustomList<T> list, Comparator<T> comparator)`
- `DataFiller<T>` — методы заполнения коллекции
- `CustomList<T> extends Iterable<T>` — `add`, `get`, `size`, `iterator`

Все реализации пишутся **против этих интерфейсов**. Менять сигнатуры — только через лида.

---

## 7. Чего НЕЛЬЗЯ делать (жёсткие ограничения задания)

-  `Collections.sort`, `Arrays.sort`, готовые реализации сортировки/поиска
-  Готовые реализации паттернов
-  Lombok (`@Builder` — только руками)
-  Push напрямую в `main`
-  Мердж без PR и ревью
-  Работа в одной ветке `main`
-  Отсутствие валидации и тестов
-  `thenComparing` в базовой сортировке (компараторы — отдельные, по одному на поле)

## 8. Git-шпаргалка

```bash
# начать работу
git checkout main && git pull
git checkout -b feature/название

# коммит
git add .
git commit -m "feat(module): description"
git push -u origin feature/название

# подтянуть свежий main перед PR
git checkout main && git pull
git checkout feature/название
git merge main
git push

# после мерджа PR — удалить локальную ветку
git branch -d feature/название
```
